```
┌────────────────────────────────────────────────────────────────────┐
│  工程护栏（一切的前提）：baseline_check + 探针回归 + git 纪律        │

   │  #2拆解 → #3方案+执行 → #4测试 │  ──产出──▶   │  试玩反馈 → #5反馈专员 →   │
   │  #1进度 → #8健康自检（7岗自转）│                │  PLAYTEST 增量 → 落地     │
   └─────────────┬───────────────┘                └─────────────▲────────────┘
                 │                                              │
   ┌─────────────▼──────────────────────────────────────────────┴────────────┐
   │  设计契约：数据驱动(JSON) + 帧strip(PNG) + 文件域隔离(W1-W5) + 占位先行     │
   └────────────────────────────────────────────────────────────────────────────┘
```

一句话：**AI 负责所有"机器可验证"的活（架构/数据/测试/文档/自动化），人工只负责"主观判断"的活（手感/乐趣/审美/拍板）**。护栏让 AI 犯错不会毁掉项目，分工让 AI 之间不打架，反馈闭环让 AI 越做越符合真人预期。

## 1. 开发日程全实录

### 1.1 第 0 天：框架下载与工程化基座（08-04 前）

- 下载并固定引擎：`tools/Godot_v4.3-stable_win64.exe`（**版本锁定 4.3**，曾有 4.6 的 godot_mcp 插件入库但明确"未拍板前不启用"——版本治理从第一天就写进文档）。
- 项目基底：一个类 Brotato 俯视角自动射击框架（内部代号 Astral Spud），已具备移动 / 自动射击 / 命中 / 接触伤害 / HUD / 金币掉落的 Phase 1 雏形。
- **08-04 一天内完成工程化基座（这是后面一切能高速运转的根）**：
  - `ce848af` 初始化 git 仓库，纳入源码/数据/美术资产，排除引擎与构建产物（`.gitignore`：引擎 133MB / `build/` / `.workbuddy/` / `tools/_*` / `*.zip`）。
  - `7accfcf` **`tools/baseline_check.py` 转正**——双阶段 headless 自校验（import PASS + runtime PASS），此后成为"不 CLEAN 不提交"的硬门槛。
  - `3da8aa8` **`tools/build_release.py` 一条命令发布**——导出 pck → 校验 exe → 实测启动 → 出分发包，任一步失败非零退出。
  - `d5256f5` **`docs/PROJECT_BRIEF.md` 交接简报**——含一段可直接粘贴的项目指令 + 新人上手 5 步，成为后续所有 Agent 的"零重复沟通"入口。
  - 当天 23:18-23:35 发起**并发冲刺**：w1-code / w2-data / w3-art / w4-narrative / w5-qa **五个并行 Agent 按文件域隔离同时落盘**，集成节点（team lead）接线 `main_scene → CharacterSelect` 并复验基线。

> 第一天就建立了三个理念：**① 机器可验的事全部脚本化；② 每个 Agent 有独占文件域不打架；③ 一份简报让新人零沟通成本接手。**

## 3. 复盘：10 条可复用方法论（精华）

> 以下按"能直接抄走"的优先级排序。前 5 条是任何项目通用的骨架，后 5 条是游戏/AI 协作场景的进阶。

### 3.1 机器可验的一律脚本化（工程护栏三件套）

- **`baseline_check.py` 双阶段 headless 自校验**：import PASS + runtime PASS，`BASELINE CLEAN` 才允许提交。这是"AI 写坏代码"的最后防线。
- **`build_release.py` 一条命令发布**：导出 → 校验 → 启动实测 → 分发包，任一环失败非零退出。
- **探针回归体系**：每个功能日新建 `tools/dayXX_check.gd` 探针，断言从 32 累积到 952；每天全量回归一遍，**探针必须双轨**——白盒直构造（快）+ 真实 GUI 点击 `push_input`（真），防止"只调函数没走界面"的假绿。
- **提交纪律**：每轮收口一个 commit 带 T 编号；改动前后各跑一次护栏；`git add` 指定文件不随手 `-A`。

> **为什么有效**：AI 的产出质量方差大，护栏把"错误是否可接受"变成"脚本说了算"，人类不用盯每个改动，只盯护栏失败。

### 3.2 主观 / 客观分离，人类只做"机器验不了"的事

- **客观项（机器可验）**：数据完整性、逻辑链路、性能帧率、无崩溃 → 全部自动化。
- **主观项（需真人）**：手感/操作跟手、难度曲线体感、Build 流派趣味、UI/UX 可读性、视觉听觉审美、剧情调性 → 汇总到 `PLAYTEST_CHECKLIST.md` 追踪区（单一事实源）。
- 自动化绝不"尝试自动试玩"，而是**标记出需人工项**，等人试玩后逐条回复。
- 验收标准书写时就分清楚：**"W5 不得判失败"** 的条目（如"华丽 VFX 观感"）直接划给人工，不阻塞机器闭环。

> **为什么有效**：乐趣、审美、手感本质不可机器验证。让 AI 在这上面死磕 = 烧 token 换主观否定。反过来，让 AI 把机器可验的全做完，人类每次试玩都是一次"高价值验收"而非"帮我跑起来"。

### 3.3 反馈闭环：PLAYTEST 增量编号 + 反馈专员岗

- 每次真人反馈登记为 **PLAYTEST 增量 #N**（单一事实源，编号递增），标记状态：🟠 待处理 / 🟢 已落地·待真人回归 / 🟡 在途。
- **反馈专员岗（#5）**每 2h 轮询追踪区：用户直接提的工作 = 最高优先级 → 交 #2 拆解 + #3 执行；落地后转"待真人回归"。
- "用户拍板"制度：关键决策编号 **F-xx**（F-01 移速×0.5 / F-13 三机制被动 / F-31 武器升级体系……），拍板内容、时间、依据全部落文档。

> **为什么有效**：真人反馈是 AI 项目最稀缺的"高质量训练信号"。编号+状态机保证**每一条反馈都有归宿**，不会漏、不会重复做、不会被覆盖。

### 3.4 岗位流水线：拆解 → 方案 → 执行 → 测试 → 健康自检

自动化岗位编排（经验证的最优形态）：
- **#2 任务拆解（每日 07:30）**：把目标日拆成函数级任务（W1 代码 / W2 数据 / W3 美术 / W5 QA），落 TASKS.md。
- **方案师（每日 08:00）**：为复杂批次产出 `SOLUTION_PLAN.md`（含实测行号、风险、回归基准）——**执行者的唯一合法输入**。
- **执行者（每日 08:30 / 12:30）**：按方案写码，每批次一收口 commit 带 T 编号，跑探针 + baseline。
- **自动化测试（每日 18:45）**：全量回归 + 数据边界 + 性能，落 TEST_REPORT.md。
- **进度分析（每 6h）**：对照规划算进度/风险，写 PROGRESS.md 日报。
- **健康自检（每日 03:00）**：最便宜，兼职"摘要一致性抽查 + 清僵尸进程 + 自动化状态巡检（PAUSED 自动恢复）"。
- **反馈专员（每 2h，高峰避让）**：见 3.3。

> **为什么有效**：职责单一、接口契约（SOLUTION_PLAN → 执行）显式化。每个岗只关心自己的输入/输出，多 Agent 不会互相踩。**但注意**：岗位间接口必须显式定义（见 3.10 事故教训）。

### 3.5 文件域隔离：并行不打架的地基

- **W1 代码（scripts/scenes）/ W2 数据（data/*.json）/ W3 美术（assets/sprites/）/ W4 剧情（events.json + LORE）/ W5 QA（只读 + TEST_REPORT）** 独占文件域。
- 团队重构后执行者 + 方案师 + 反馈专员同样按文件域隔离：方案师写 `SOLUTION_PLAN.md`，执行者写代码/数据，反馈专员写 `PLAYTEST_CHECKLIST.md`。
- **数据只读原则**：自动化轮只读 `data/*.json` 分析，写数据走 Excel 管线或由执行者独占，防止双写冲突。

### 3.6 数据驱动 + 增字段不改结构

- 新增角色/怪物 = 一张帧 strip PNG + 一条 JSON 记录，**代码零改动**（DataLoader 自动缓存）。
- 第一天差异分析就判定"全部是增字段而非改结构"，DataLoader 全程零重写。
- **帧 strip 硬契约**：横向排列、帧宽=精灵尺寸（4 帧@32 = 128×32）、SpriteFrameFactory 运行时切帧。
- **Excel 单一事实源**（阶段 F 升级）：`docs/GameData.xlsx` → `excel_export.py`（--check-only 校验）→ `data/*.json`（禁手改）。

### 3.7 占位先行 + 幂等工具

- **美术/音频/剧情占位先行**：功能缺口一律占位纯色图/程序合成音，保证功能可检测；表现层主观项交人工。
- **幂等生成工具**（gen_*.py）：可重复跑、断点续跑不重复烧钱（`--skip-c` 复用母图），量化色板用 `COLOR_DICT.json`（ΔRGB≤12 归并）。

### 3.8 数值方法论：对照表 + 只校准有证据的目标

- 平衡结论必须**表格化**：DPS 上限参照表 / 敌 HP 梯度 vs 玩家 DPS 对照 / Boss 击杀时间估算。
- **只校准有证据的目标**（如"wave1 首升 ≥30"→ chaser 2→3）；无法确证的就登记为"观察项"归 Day N 统一决策，**不臆造调值**。
- 数值改动必须过探针：叠加边界（乘法/除法还原零漂移）、公式对照表、消费点覆盖。

### 3.9 自动化瘦身与成本治理

- 产出密度评估：连续多轮"持平轮/确认轮"的岗位 → 降频 / 合并 / 删除（实测 10→7，省 TOKEN ≈45-55%）。
- **高峰避让原则**：自动化避开用户活跃时段（09-12 / 14-18），清晨完成拆解→方案→执行早班，晚间收测试与反馈。
- 每个岗位 prompt 里的频率文案与实际 rrule 同步，防止自动化自我误读。

### 3.10 风险治理：技术债台账 + 决策拍板机制 + 接口契约

- **技术债台账**（TECH_DEBT_ISSUES.md，T-001~054）：逐条编号、标级别（P0/P1/P2）、归口、状态；阶段 F 专项整改。
- **决策拍板机制**：悬而未决的关键决策标 `[!] 待 Owner 拍板`（如攻击力口径 R4、护甲公式口径），绝不擅自替用户定。
- **接口契约**（最大教训）：Day 18-19 空转 13 小时的根因就是"方案师产出物格式"与"执行者消费条件"没对齐。**任何岗位拆分后必须同步校验上下游接口**（自动化瘦身计划的"联动风险"章节就是这个意识）。

## 4. 给新 Agent 的一键启动手册

> 目标：你在一个**全新的 Godot 项目**（或任何游戏引擎项目）里，用我们的方法从零/从框架开始做，跑出同样的效率。

### Step 0：读三份文档再动手（15 分钟）

| 文档 | 作用 |
|---|---|
| `docs/PROJECT_BRIEF.md` | 项目指令（可直接粘贴到项目组"指令"框）+ 运行/构建命令 + 架构分层 + 5 条约定 + 新人上手 5 步 |
| `docs/GDD.md` + `docs/ART_STYLE.md` | 设计源 + 美术技术基底（网格/色板/描边/透明键/帧 strip） |
| `docs/GIT_COLLAB.md` | 仓库协作、SSH-over-443 通道、质量护栏 |

### Step 1：拉起工程护栏（半天，一劳永逸）

```bash
# 1. 固定引擎版本，锁定工具链
tools/Godot_v4.3-stable_win64.exe --version

# 2. baseline 自校验脚本（双阶段 headless）—— 不 CLEAN 不提交
python tools/baseline_check.py          # 输出 BASELINE CLEAN

# 3. 一条命令发布构建
python tools/build_release.py --zip

# 4. git 初始化 + .gitignore（排除引擎/构建/临时产物/AI 记忆目录）
git init && git add . && git commit -m "chore: init repo with guardrails"
```

### Step 2：搭自动化流水线（WorkBuddy 或任意 agent 调度平台）

建 7 个岗位，每个岗位一份 prompt，写清楚"读什么 / 写什么 / 何时跑 / 护栏是什么"：

| 岗位 | 频率 | 输入 → 输出 | 关键护栏 |
|---|---|---|---|
| #2 任务拆解 | 每日 07:30 | 规划文档 → `TASKS.md`（函数级） | 未拆解前执行者不写码 |
| 方案师 | 每日 08:00 | TASKS.md → `SOLUTION_PLAN.md`（含实测行号/风险/回归基准） | 方案是执行者唯一合法输入 |
| 执行者 | 每日 08:30/12:30 | 方案 → 代码 + 探针 + commit | 每批次一收口 commit 带 T 编号；改前后跑 baseline |
| 自动化测试 | 每日 18:45 | 全代码 → TEST_REPORT（回归 + baseline） | 回归全绿 + BASELINE CLEAN |
| 进度分析 | 每 6h | 规划 vs git 实测 → PROGRESS 日报 | 只分析不写码 |
| 反馈专员 | 每 2h（高峰避让） | 人工反馈 → PLAYTEST 增量编号 + 拆解派发 | 用户直派 = 最高优先级 |
| 健康自检 | 每日 03:00 | 全自动化状态 → LOOP_HEALTH 日志 | PAUSED 自动恢复；不删文件不改他人产出 |

**高优先级三连**（抄作业必做）：
1. **探针制度**：每个功能日新建 `dayXX_check.gd`，断言累积，全量回归。
2. **PLAYTEST 追踪区**：`PLAYTEST_CHECKLIST.md` 单一事实源，增量编号 + 状态机（🟠待处理/🟢已落地/🟡在途）。
3. **用户拍板编号**：关键决策 `F-xx`，拍板内容/时间/依据落文档。

### Step 3：用我们的"开发日模板"跑迭代

每个功能日按这个节奏（建议抄成模板）：
1. **#2 拆解**成 W1/W2/W3/W5 函数级任务（标注文件域，防冲突）。
2. **方案师**对复杂批次落 SOLUTION_PLAN（含实测行号，防"我以为"）。
3. **执行者**按批次 A/B/C 顺序实现，每批次一收口 commit（带 T 编号）+ 探针 + baseline。
4. **#4 测试**全量回归 + 阶段报告。
5. **人工试玩** → 反馈增量 → 反馈专员拆解 → 回到 1。

### Step 4：遵守 6 条铁律（我们的血泪总结）

1. **不 CLEAN 不提交**（baseline 双阶段）。
2. **机器可验的全自动化，主观项全标记给人工**。
3. **数据驱动 + 增字段不改结构**；跨系统数据改走单一事实源管线。
4. **用户拍板前不臆造设计**；悬而未决标 `[!] 待 Owner`。
5. **岗位接口显式化**：改了上游岗位，必须校验下游消费条件（Day 18-19 教训）。
6. **每轮收尾 commit + push**，远端永远最新（本地=主仓库，远端=备份镜像）。

### Step 5：遇到事故时的处置模板

```
1. triage：复现 → 编号 BUG-00x → 归口（哪个岗/哪条数据/哪个系统）
2. 拆解：P0 用户反馈最高优先；拆成最小可验证任务
3. 修复：改 → 探针固化（断言覆盖此 bug）→ baseline → commit
4. 回归：全量探针必须全绿，防"修 A 坏 B"
5. 复盘：根因落文档（是数据？是接口？是护栏缺口？）→ 补护栏
```
